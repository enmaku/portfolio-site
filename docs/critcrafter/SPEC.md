# CritCrafter character viewer: v1 spec

The settled v1 spec for the **CritCrafter** character viewer: a phone-framed mobile project in this repo at `/projects/critcrafter?id=<Pathbuilder id>` that loads a **Pathbuilder export** and shows it in a mobile-first layout with a bottom button bar cycling Stats, Skills, Gear, Spells and Actions. It is a table-play companion for a player who forgot their sheet: it does not create or edit sheet contents, but keeps minimal table-state tracking.

This file is authoritative. It came out of the wayfinder map (issue #476) and its tickets; those become history. Detail lives beside it:

Terms (**CritCrafter**, **character viewer**, **Pathbuilder export**, **rules corpus**, **CritCrafter sheet**, **Breakdown**, **Features**, **Action source group**) are defined in `CONTEXT.md`. Say "character", never Strength of Thousands' "hero". The sibling repo `~/code/strength-of-thousands` is a reference only (`src/domain/pathbuilder.js`, `heroes/*.json`, `cards/generate_cards.py`), never a dependency.

## Architecture in one picture

```
browser ── GET pathbuilder2e.com/json.php?id=N ──▶ { success, build }     (CORS *, no Cloudflare challenge in a browser)
browser ── POST { success, build } ──▶ critcrafterSheet (Firebase function, App Check)
                                         │  derived stats (functions/critcrafter/)
                                         │  name resolution ◀── Firestore rulesEntries (Admin SDK only)
browser ◀── CritCrafter sheet JSON ──────┘
browser renders the sheet; the Pinia store adds table state (localStorage, by Pathbuilder id)
```

The viewer renders and does no rules lookup or derived-stat math. The only arithmetic it does is recombination of sheet numbers with table state (live AC, hands limit, HP, rests).

## Access and routing

The route is `/projects/critcrafter?id=<digits>`, nothing else: no hash, no extra state, so the URL stays stable and shareable. The SoT Heroes-page button (implemented separately) always builds this `?id=` form from the stored Pathbuilder id. With no `id` the viewer shows a landing state: one input accepting a bare id or a full Pathbuilder URL (digits, or any URL with `?id=N`, the SoT `parsePathbuilderId` rules), normalised to the numeric id and written into the URL. On every load the browser fetches `https://pathbuilder2e.com/json.php?id=N`, posts the response body to the sheet function and renders the returned sheet; nothing is cached client-side (offline and PWA caching are out of scope). Pasting or uploading an export is not in v1. The browser fetch is mandatory because Pathbuilder answers any scripted client (curl, any server) with a Cloudflare 403 challenge (`cf-mitigated: challenge`), but a browser on another origin gets HTTP 200 with `access-control-allow-origin: *`; a plain GET needs no preflight (a custom request header would fail the allow-list), so the viewer sends none. The body is `{"success":true,"build":{…}}`; an unknown id is HTTP 404 `{"success":false,"error":"Build not found."}`, also readable cross-origin; the response is `no-store`, so nothing is cacheable. Pathbuilder publishes no API, rate limit or terms, ids are sequential, and a build is already public to anyone with its id, so v1 adds no access control: the commitment is relay and render only, nothing stored. Four failure states, each with its own message: (1) network or CORS failure, "couldn't reach Pathbuilder" (Retry); (2) HTTP error other than 404, "Pathbuilder is unavailable" (Retry); (3) 404, or 200 without a `build` (including a 200 whose body is not JSON), "build not found or no longer shared" (offer "try another id", no Retry); (4) any sheet function failure, "CritCrafter couldn't build this sheet" (Retry, hidden for `invalid_build`). Not probed in the research: private or deleted builds, behaviour under load, Safari and Firefox.

## Corpus

Rules text lives in one Firestore collection, `rulesEntries`, built from the Foundry `foundryvtt/pf2e` packs (`packs/pf2e/`), not hotlinked from Archives of Nethys and not a Foundry module in git (see ADR 0031). Document id is `<type>:<foundry-slug>` (with a `-<pack>` suffix on slug collisions); types are feat, spell, action, classFeature, heritage, background, equipment. Fields: name, `nameKey` (lowercased, punctuation-normalised), type, level, traits, `actionType`/`actions`, bulk, price, spell rank/defense/duration/area, sanitised `description` HTML, `aliases: string[]`, and licence data `license` (ORC or OGL), `remaster` and source book `title` from `system.publication`; entries without publication data are skipped. Effects, bestiaries, deities, conditions and journals are out of v1. At ingest, `@UUID[...]` links become inert `<a data-ref>` markers (or AoN search links when unresolvable) and Foundry enrichers (`@Damage`, `@Check`) flatten to plain text. `rulesMeta/current` holds `{sha, ingestedAt, counts}`. `firestore.rules` denies all client reads and writes; only the function reads, via the Admin SDK. Facts that drove this: the packs hold about 16.9k relevant entries (about 14.5 MB raw, 3.8 MB gzip trimmed; about 26 MB raw and 6 MB gzip for everything displayable, which is why shipping the corpus to phones was rejected); each entry carries a machine-readable licence tag (feats: 4814 ORC-remaster, 1496 OGL-legacy, 171 OGL-remaster), so the correct notice can ride on every entry; 231 of 19.7k names are ambiguous across packs. Licence: embedding rules text is permitted under the ORC (OGL 1.0a for legacy content) with the III notices, no implied endorsement and no Reserved Material (setting proper nouns, art, logos); rewritten text is share-alike; the Pathfinder logo and compatibility claims need the separate Compatibility License; the Foundry repo's Apache code licence and its Paizo/Foundry agreement do not extend to us, so the per-entry tag is our basis and the packs are only a structured source. AoN's own Community Use licence is not ours and AoN has no API terms; its Elasticsearch endpoint rejects non-localhost origins in a browser, so it is used only server-side at ingest, for the alias pairs. Counsel review of the ORC share-alike boundary and AoN's compilation layer is an open caveat that ships with the licence notice. Name resolution happens in the function: exact `nameKey`, then alias, then miss. Aliases come from AoN `legacy_id`/`remaster_id` pairs (same category, distinct names; about 175 spell and 210 feat renames) plus a committed JSON of Pathbuilder labels (`Repair Kit`, `Clothing (Explorer's)`, `Detective Dedication` for `Edgewatch Detective Dedication`, `Smuggler's Sack II`). Exact match is authoritative because the export name is the author's edition choice (exports mix legacy and remaster names with no edition flag); ambiguity resolves to the remaster entry, then by the `type` hint of the export field the name came from; the notice shown is that of the entry whose text is displayed. Foundry renames in place with no rename metadata and usually deletes the legacy entry, so legacy names survive only as aliases. Against the six sample exports 236 of 275 distinct names match exactly, 4 more via alias, and the 35 misses are not drift (framework specials, `Not set` deity, custom content, generic scrolls, Pathbuilder labels), so about 14% unresolved is normal. A miss is never given a placeholder or hand-written entry: the function returns the name, `rules: null` and an AoN search URL (null for custom content). The exception is `Scroll of <Spell>` and `Wand of <Spell>`: the function looks the spell up normally and the generic `Scroll|Wand of Nth-rank Spell` item by the spell's rank, returns both texts separately (the item's `linked[]`), and a spell miss makes the whole item a miss. Talismans, potions, cantrip decks and other families are out of v1. Ingest is a manually run Node script in `scripts/` reading a local clone at a pinned SHA and writing with the Admin SDK; it upserts every entry, then deletes docs not seen, so the corpus mirrors the pinned SHA. Operating it is in [runbook.md](runbook.md).

## Function boundary

`critcrafterSheet` is an `onRequest` HTTPS function (not callable), `us-central1`, 512 MiB, `minInstances: 0`, `maxInstances` about 10, 30 s timeout, `cors: true` (as the BGG proxy, because the owner may call it from other projects). POST only (`405 method_not_allowed` otherwise); the body is the `json.php` response verbatim and the function reads `.build`. Success is `200` with the sheet. Limits: 1 MB, checked on `Content-Length` and again on the parsed body; non-JSON is `400 bad_json`, oversize `413 too_large`, a missing or non-object `build` `422 invalid_build`; nothing else is validated, because everything else degrades through `warnings[]`. Errors are `{ error: { code, message } }` with stable codes `method_not_allowed`, `app_check_failed` (401, the handler verifies the `X-Firebase-AppCheck` token itself because `enforceAppCheck` is callable-only; skipped in the Functions emulator), `bad_json`, `too_large`, `invalid_build`, `rate_limited`, `internal`; client errors (4xx, including `app_check_failed`) log as `warn` under `critcrafter.error` and 5xx as `error`, with the same non-identifying fields; the viewer maps every non-2xx and every network failure to this endpoint to the one "CritCrafter couldn't build this sheet" state. Abuse and cost control is Firebase App Check (reCAPTCHA) enforced plus the `maxInstances` ceiling; there is no per-IP rate limiting in v1 (the code `rate_limited` is reserved) and no billing budget or alert (owner decision: usage is insignificant). Other projects reusing the endpoint register for App Check themselves; CORS is open and App Check is the real gate. There is no response cache by export hash, since that would mean storing exports; the only cache is a bounded in-memory cache of corpus entries per warm instance, cleared on recycle. Targets, documented but not enforced: warm under about 2 s, cold under about 5 s for a typical build. Logging is structured and non-identifying only: request id, request bytes, response bytes, duration, corpus SHA, and warning codes with counts; never the body, names, item names or `warnings[].detail`. The function never sees the Pathbuilder id. Firebase request logs keep default retention. The function code lives in `functions/critcrafter/` as plain CommonJS (Node 20), one file per concern (abilities, skills, saves, spells, gear, HP), exported from `functions/index.js` beside the BGG functions.

## Sheet format

The CritCrafter sheet is a versioned envelope `{ schemaVersion, generatedAt, corpus: {sha}, warnings[], header, stats, skills, gear, spells, actions, features }`, one key per screen, defined by [sheet.schema.json](sheet.schema.json). Evolution is additive-only within a version: the viewer ignores unknown fields, and an unknown `schemaVersion` shows a hard "reload to update" state (the only check the viewer makes at runtime). The function logs response size; v1 sets no size budget or cap. All rules text is inline (lazy detail fetch is a v2 option). Every derived number is a **Stat** `{ value, breakdown: [{label, amount, type}], actions? }` with `type` one of ability, proficiency, level, item, status, circumstance, untyped, base; the function guarantees `sum(amount) === value`, and where Pathbuilder precomputes a total and the rebuilt parts disagree, Pathbuilder's value wins and an "Other (from Pathbuilder)" line carries the difference, plus a warning. Every resolved name has the common entry shape `{ key, name, kind, traits[], cost, level?, rules, aonUrl }`, where `rules` is `{html, license, remaster, source}` or `null` for a miss, and `cost` is `{kind: actions|reaction|free|time|null, min?, max?, label?}`, never a parsed string. Scrolls and wands carry `linked[]` with the spell. Keys are deterministic from the export (`<section>:<normalised-name>#<nth occurrence>`, slots `slots:<casterKey>:<rank>`), so the same input gives the same keys and the corpus SHA never enters a key, which means a re-ingest does not wipe tracked state. Array order is display order. Screen shapes: `header` (identity, max HP, Perception, Speed, unarmored AC; placeholders such as `Not set` and `None selected` normalised away, and alignment is never shown), `stats` (abilities, saves, class DC), `skills` (16 core skills then lores), `gear` (groups weapons, shields, armor, consumables, gear, with `qty`, `bulk`, `price`; weapons add `hands`, `versatile`, attack and damage Stats, range, reach; armor carries an `acTotal` Stat as if worn alone; shields carry `acBonus`, `hands`, `buckler`, `hardness`, `hp`, `bt`; `gear.bulk` is a Stat summing listed items with limits 5 + Str and 10 + Str), `spells` (casters with attack, DC, slots per rank and rank groups; one `focus` section; `rituals`), and `actions` and `features` as grouped entries. `warnings[]` records everything swallowed (unmatched names, breakdown residuals, dropped pseudo-casters, unknown `mods` labels, unparseable familiar names), has no viewer UI in v1, and the function fails only on a non-object `build`. Deliberately left out: eidolon, animal-companion and familiar stat blocks (familiar abilities appear only as actions), container structure, ABP and variant rules, layered armor, conditions, per-day ability tracking, Pathbuilder's ability-boost `breakdown`, the `"Invested"` flag, and any hand-written stat explainer prose. The contract is the schema alone: function tests and viewer tests both validate fixtures against it (no code shared across the CommonJS and ESM sides), and what a schema cannot say (sum invariant, key scheme, ordering) is stated in its top-level `description`.

## Derived stats

Computed in the function, each with a sum-checked breakdown: 16 core skills and lores, saves, Perception, class DC, spell attack and DC per caster, focus attack and DC, max HP, speed, bulk with limits, each weapon's attack and damage, each armor's AC and the shield bonus; ability scores and mods have no breakdown. MAP, reach and range are not stats (range and reach come from corpus traits). The export holds proficiency ranks (not totals), final ability scores, name-only gear and spells, and already-computed weapon `attack`/`damageBonus` and `acTotal` (with components); skills, saves, Perception, class DC, spell DCs, max HP, speed and bulk are not in it. Default rules are assumed and **not applied** in v1: Proficiency Without Level and other variants, armor check penalty, armor speed penalty, Strength requirements, size adjustment to bulk limits, and any circumstance or status bonus not in `mods`; level is added only for trained or better, so untrained is the ability mod alone. These are listed in the viewer's about text, not per stat. `mods.AC` is counted once: when the gap between Pathbuilder's `acTotal` and the rebuilt components is exactly the AC mods total, Pathbuilder already included them and no "Other (from Pathbuilder)" line is added; otherwise the mods are added on top of the components (no export fixture carries an AC mod, so this is covered by synthetic tests). Every `mods[label][bonusType]` becomes a breakdown line on the stat whose label matches (skills, Perception, saves, AC), typed from the bonus type; unknown labels or types produce a warning. Weapon attack is rebuilt (ability + rank for the category or `specificProficiencies` + level + potency); damage is one untyped "Pathbuilder damage bonus" line plus a separate dice string, with no Strength decomposition. Armor AC is built from `acProfBonus`, `acAbilityBonus` and `acItemBonus`; `shieldBonus` arrives as a string and becomes its own number. Spells and focus: each real, archetype and innate caster gets attack and DC from ability + proficiency + level; `Other Spells (Staves etc)` gets null attack and DC plus a warning (its proficiency is unreliable); focus is one attack and DC from the highest-bonus entry when several traditions exist, with a warning listing the others; `spells` and `prepared` are unioned because `prepared` is not a subset of `spells`. Bulk comes from corpus `bulk` (Rope is 0.1, light); unmatched items count 0 and appear as a labelled breakdown line, never guessed. **Max HP** is `ancestryhp + (classhp + conMod) × level + bonushp + bonushpPerLevel × level`: `bonushp` is a flat total, not per level (the formula in `pathbuilder-records/docs/08` multiplies it by level and is wrong). Verified against two real exports: a Toughness-only Dwarf Fighter (level 5, Con +3, `bonushp: 0`, `bonushpPerLevel: 1`) shows 80 HP, and the same character with Barbarian Dedication and Resiliency (`bonushp: 6`) shows 86 HP; the old form gives 110. Both are kept as goldens in `fixtures/`. Export irregularities the code must tolerate: `feats` tuples of length 4 or 7 with a non-null element 1 (`["Skill Training","Intimidation",…]`); `equipment` tuples of length 3 or 4, containers possibly unreferenced; `"None selected"` and `"Not set"` placeholders; duplicates in `specials` and spell lists; stray non-rule `specials` (`acid`, `Soul`); `size` as an ordinal (use `sizeName`); pseudo-casters (`Other Spells`, `Cleric Font`, innate ancestry casters still typed `prepared`, `Archetype <X>`); eidolons not in `pets`. Reference for the port is SoT `src/domain/pathbuilder.js` (id parsing, mod and proficiency math, class-line logic are reusable; known bugs not to copy: `computeSave` ignores `mods`, one-caster spell stats, `pickPrimaryWeapon` tests nonexistent fields, `computeProficiencies` reads a `shield` key that is never exported). `generate_cards.py` is a specification, not portable code. Tests: the six SoT exports (`build` only) plus the two Dwarf Fighter exports as fixtures with golden tests per stat and breakdown, the sum invariant checked on every Stat of every fixture, and hand-built synthetic builds for untrained, `mods`, dual class, nonzero HP bonuses, a high-rank caster and a raised shield; one or two builds are hand-verified against Pathbuilder's own screen with the fixtures README saying which. Pets, eidolons, runes and high-rank casters wait for real exports.

## Screens and state

The screens are specified in [the layout doc](../prototypes/critcrafter-viewer-layout.md), which is the screen reference; the prototype code (`src/pages/projects/Critcrafter*.vue`, dev-only route `/projects/critcrafter-prototype`) is throwaway reference, not a base to build on. Summary: a phone-framed project inside the existing project shell (desktop phone frame unchanged, mobile-only in v1), a floating bottom bar (Stats, Skills, Gear, Spells, Actions), a pinned topper (name, level, ancestry/class line, HP, AC, Perception, Speed, plus a small shield row when a shield is equipped), site palette only, 52–56 px rows, 48 px touch targets, and a bottom sheet for all detail. **Stats**: Saves, Abilities, DC & attack sections, a rest row, and a collapsed **Features** expansion at the bottom holding passive feats and class features. **Skills**: one column with the full U T E M L ladder and aligned bonus. **Gear**: Bulk n / limit, then Weapons, Shields, Armor, Consumables, Gear groups. **Spells**: per caster then rank, one Focus section across casters, then Rituals. **Actions**: grouped by source (Class, Ancestry, General, Archetype, Familiar, Basic actions, Exploration, Skill actions), sorted free, 1, 2, 3, reaction; the first five groups open, the last three collapsed. What fills each screen: Actions lists every available action built the way the SoT card generator does but without its exclusions (feats, specials, familiar abilities, linked actions a cost-less class feature embeds, plus the universal basic, specialty basic, exploration and per-skill actions), classified from corpus `actionType`/`actions`, with pets and eidolons out; a cost-less class feature that embeds an action (Spellstrike) stays in Features as passive text and its embedded action appears once on Actions under Class; unmatched specials (`acid`, `Soul`, `Low-Light Vision`) are dropped silently; duplicates with the same name and option merge into one row marked ×n, while different options stay separate rows. Gear weapons come from `weapons[]`, Armor and Shields from `armor[]`, `equipment` splits into Consumables and Gear by corpus item category, containers are ignored, and misses go to Gear name-only. Collapsed row: name, trait chips, cost glyph (spells, actions) or stat text (gear), quantity; bottom sheet: rules text, bulk, price, range, duration, defense and licence tag; a miss shows the name plus an AoN link and no placeholder text. Unmatched armor and shields never get stand-in numbers: armor `acTotal` and shield `acBonus`, `hardness`, `hp`, `bt` are `null` (with `armor_ac_unknown` / `shield_bonus_unknown` warnings), live AC then ignores them, and an unmatched weapon assumes one hand with a `weapon_hands_assumed` warning. Pathbuilder weapons carry no held state, so every weapon starts put away. **Table state** (the one exception to "read-only", which means no creating or editing sheet contents): spell slot and focus usage, consumable consumed counts, armor, weapon and shield equip toggles, raise and lower shield with live AC, the two-hand limit, current HP, temp HP and per-shield current HP, kept in a Pinia store persisted to `localStorage` keyed by Pathbuilder id (the repo's existing Pinia/`localStorage` pattern), storing deltas only so the sheet stays the source of truth, in memory only if storage is unavailable, with no server side and no cross-device sync. Stale keys are ignored, there is no export fingerprinting, and one **Reset tracking** action (with confirm) clears a character's state. Live AC is `(worn armor acTotal, else unarmored AC) + (shield raised ? shield acBonus : 0)`, one body armor at a time. Hands: weapons use sheet `hands`/`versatile`; a shield takes one hand while equipped, a buckler only while raised; equipping or raising a shield puts weapons away (earliest first) until it fits, and equipping a weapon or widening a grip drops other weapons, then the shield (a buckler is lowered). HP: tap HP for a keypad sheet (Damage, Heal, Temp HP; temp HP absorbs first and does not stack, HP floors at 0); on a raised shield the keypad adds Damage Shield and Repair Shield. Rests: Refocus (10 minutes, +1 focus), 8 h (regain Con mod + 1), 24 h (2 × that), Extended (full HP); every 8 h or longer rest refills slots and focus and clears temp HP; rests never repair shields (repairing is a skill-check action) and never reset consumables. There are no conditions in v1 (no dying, wounded, doomed or drained) and daily-use abilities are not tracked. **Tap-to-explain**: the number itself (48 px, dotted underline) opens one breakdown sheet for AC, saves, Perception, skills and lores, class DC, spell attack and DC, weapon attack and damage chips only, HP max only, speed and bulk, showing total, ordered rows with bonus-type chips, a Total row, then linked corpus actions (stacked detail sheet, Back returns), with no prose; the AC breakdown shows current state only, Bulk ignores equip state, and "Other (from Pathbuilder)" and "Untrained +0" render as plain rows. Trait chips are plain labels in v1.

## Loading states

Mobile-only: no desktop layout in v1. While loading, one full-screen state with the bar hidden shows a skeleton of the topper and a few ruled section blocks plus one status line that follows the step ("Fetching from Pathbuilder…", then "Building your sheet…"), with no spinner-only screen and no timeout UI beyond the four failure states. The landing state shows the id-or-URL input with the hint "Paste your Pathbuilder id or share link" and a Recent row of the last three successfully loaded ids, labelled with the character name, kept in `localStorage`. Every load refetches and re-posts; stored table state is clamped to the new sheet's maxima (slots, focus, HP, consumables) with no notice or migration UI. Empty states: the Spells bar item is hidden when there are no spells, rituals or focus (a four-item bar), empty groups are omitted, and a visible screen with nothing shows one muted line (for example "No gear in this build"); Stats is always populated.

## Share metadata

`/projects/critcrafter` gets exactly one share-catalog row with `pasteUnfurl: true`; `?id=<id>` links unfurl as that same generic card, because the site is a static host and no character name or build may reach chat crawlers. There is no per-id metadata and the loaded viewer does not retitle the tab with a character name. The card has title `CritCrafter`, a one-line description (a mobile viewer for Pathbuilder characters: stats, skills, gear, spells, actions at the table), a new favicon id and a new `icons/social/critcrafter.png` Open Graph image, with the one-action glyph (`src/assets/critcrafter-prototype/action-single.png`, copied from the SoT card templates) as the icon basis. The glyph's provenance and licence must be confirmed before it ships as site branding, since the prototype only used it as in-UI cost art. The viewer is not installable in v1, but the launcher icons (192 and 512 PNG, with a launcher colour in `APP_ICON_COLORS`) are produced so adding it later is one line plus a manifest entry; it is not added to the installable list now. CritCrafter is added to the "Mobile" section of the nav in `MainLayout.vue` with the new icon. The prototype route stays dev-only, with no catalog row and no nav entry (it is already gated by `import.meta.env?.DEV` in `src/router/routes.js`).

## Ops and tests

Ingest and monitoring are in [runbook.md](runbook.md); in short, ingest runs on demand only (no schedule, no CI) when newer Foundry content is wanted or a name-drift cluster appears in `warnings[]` counts, is a dry run by default with `--apply` and a 10% delete/count guard, is rehearsed against the Firestore emulator (port 8080) before production, and rolls back by re-ingesting the previous pinned SHA; there is no staging project and no backup job. Cost is cents per ingest (about 20k writes and 20k reads) and normal use is insignificant. Monitoring is the structured logs plus two saved Logs Explorer queries, with no dashboards or alert policies; after each ingest the warning-count query is a regression check. Tests are `node:test` only, matching the repo: function tests (derived-stat goldens, name resolution, handler errors, schema validation of output) under `functions/critcrafter/`; viewer tests for the per-id store (slots, focus, consumables, equip, shield raise, hands limit, HP, temp HP, shield HP, rests, clamping), pure view-model helpers (live AC composition, hands enforcement, grouping, section hiding) and the route and share-catalog row; no `.vue` component tests, no jsdom, no Playwright e2e in v1, so `.vue` files stay thin. Viewer fixtures are sheet JSON generated by running the committed exports through the function, validated against [sheet.schema.json](sheet.schema.json) by a test, rebuilt by a regenerate script on schema change and never hand-edited. Committed exports have names and free-text fields stripped and the rest byte-for-byte. Wiring: `npm test` already globs `src/features/**/*.test.js`, so viewer tests under `src/features/critcrafter/` are picked up with no change, but `functions/critcrafter/**/*.test.js` is not in the script and must be added (the script lists function tests by file today). Still-wanted real exports (a pet or companion, an eidolon, runes on gear, a high-rank caster) are post-launch; until they arrive, synthetic builds cover those cases.

5. Viewer shell: route, landing, relay fetch, loading and error states, share card, nav entry, icons. Starts on fixtures after 1. Blocks 6, 7, 8.
6. Stats screen: topper, ruled sections, tap-to-explain. After 5.
7. Skills, Gear, Spells and Actions screens. After 5.
8. Table-tracking store with HP keypad, rests and shield. After 5.
9. Test globs, licence notice and launch hardening. Last (after 4, 6, 7, 8).

**Ship-blockers** (ticket 9 cannot close without them): first production ingest done and verified; App Check registered with a reCAPTCHA key; the licence notice rendered, with the counsel caveat recorded; the action-glyph provenance and licence confirmed; the prototype route dev-gated or removed (already dev-gated today, verify it stays so); and a nonzero HP-bonus export fixture present (satisfied by the two Dwarf Fighter exports already committed, so this reduces to confirming they stay and drive goldens). **Out of scope for v1:** offline use and PWA caching; client-side lookup or derived-stat computation; editing sheet contents or anything resembling the character builder; condition tracking and per-day ability tracking; the SoT Heroes-page button; pasting or uploading an export.
